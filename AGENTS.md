# Finance Manager Agent Rules & Behavioral Constraints

## 1. Meta-Rules & Execution Boundaries
* **Package Manager — npm Only:** This project is set up with `package-lock.json` in both `frontend/` and `backend/`. NEVER introduce `yarn.lock` or `pnpm-lock.yaml`. All package operations MUST use `npm` (`npm install`, `npm uninstall`, `npm run <script>`). If a lockfile conflict arises, delete `node_modules` and `package-lock.json` in the affected workspace, then run `npm install` again — don't hand-edit the lockfile.
* **No Silent Duplicate Definitions:** Before adding a method to a `services/*.js` object literal, `grep` the file for that key first. A second property with the same name silently overrides the first with no error — this project has already shipped a duplicate `updateExpense` definition that shadowed a working implementation. Never leave two definitions of the same key in one object.
* **Never Call a Method That Doesn't Exist on `this`:** If a service method does `this.someHelper(...)`, `someHelper` must be defined in that same service object (or imported and invoked explicitly, e.g. `otherService.someHelper(...)`) before that code ships. This project previously had `expenseService` calling `this.updateBudgetSpent()`, a method that only existed on `budgetService` — every add/edit/delete of an expense threw *after* the database write already succeeded, so the UI showed an error toast on data that had, in fact, saved. Cross-service calls must go through the imported service object, not `this`.
* **Zero Placeholder Policy:** Never output placeholders, incomplete structures, or `// TODO: implement later` comments in controller/service/component code. Every block must be fully implemented before commit.
* **Verification Before Import:** Before importing a new npm package, check it's already listed in the relevant `package.json` or run `npm ls <package>` in that workspace. Don't assume a package is present from memory or from what the other workspace (frontend vs. backend) has installed — they have separate `node_modules`.
* **Defensive Commits:** Create a git checkpoint before any multi-file structural refactor. Don't modify more than 3 files in a single pass without surfacing a summary of what changed and why, so a human can review before the next step builds on it.

## 2. Frontend Constraints (React + Vite + Tailwind + Clerk)
* **Data Flow:** Pages (`src/pages/*.jsx`) own data fetching (`useEffect` + `api` calls) and pass data down as props to presentational components in `src/components/**`. Don't fetch data inside a deeply nested display component if the parent page already has it — pass it down instead.
* **Component File Integrity:** When creating a new component file, its contents must match its filename and its usage. Before finishing a component, re-open the file and confirm the exported component's name and prop signature actually match what's imported elsewhere (`grep -rn "ComponentName" src/`). This project has shipped a file where `RecentTransactions.jsx` contained a copy-pasted duplicate of `SpendingChart.jsx` — same file extension, wrong component, and no build-time error caught it because both were valid JSX.
* **Refetch After Mutation:** Every add/edit/delete handler must re-fetch the affected list (or update local state to match) before considering the interaction complete. Users should never need to manually refresh the page to see the result of their own action.
* **Auth Token Source:** Get the current Clerk session token exclusively from `useAuth()`'s `getToken()` (imported from `@clerk/clerk-react`). Never call `.getToken()` on the object returned by `useUser()` — the user profile object has no such method. Store the resolved token in `localStorage`/`AuthContext` state; `api/client.js`'s request interceptor reads it from there.
* **Styling Integration:** Use Tailwind utility classes directly, backed by the shared component classes in `index.css` (`.btn-primary`, `.card`, `.input-field`, `.badge-*` — see `DESIGN.md`). Don't hand-roll a new button or card style inline when an existing class covers the case.
* **Icon Discipline:** Import icons exclusively from `@heroicons/react/24/outline` as named imports. Follow the semantic pairings and size scale documented in `DESIGN.md` (`w-6 h-6` stat icons, `w-5 h-5` row actions, `w-4 h-4` inline glyphs).

## 3. Backend Constraints (Express + MongoDB + Mongoose)
* **Decoupled Architecture:** Maintain the existing separation: `routes/*.js` wire URLs to controller functions and apply `authMiddleware`; `controller/*.js` validate the request body/params and shape the JSON response; `services/*.js` contain the actual Mongoose queries and business logic; `model/*.js` defines schemas only. Don't put `mongoose.find()`/`.save()` calls directly in a controller — route them through the matching service.
* **User Scoping:** Every query against `incomeModel`, `expenseModel`, or `budgetModel` must filter by `userId: req.user._id` (set by `authMiddleware`). There is no separate "admin" bypass in this codebase — a missing `userId` filter is a data-leak bug, not a convenience shortcut.
* **Budget Sync on Mutation:** Any code path that creates, updates, or deletes an expense must keep the corresponding `budgetModel.spent` total in sync by calling into `budgetService.updateBudgetSpent(userId, category, month, year)` (directly, or via `expenseService`'s `updateBudgetSpent(userId, category, date)` wrapper). Don't add a new expense-mutation path that skips this.
* **Response Envelope:** Every controller response is `{ success: boolean, message?: string, data?: ... }` (the two `getAllExpense`/`getAllIncome` list endpoints are the sole legacy exception, returning a bare array — match the existing pattern for the resource you're touching rather than mixing styles within it).
* **Payload Validation:** Controllers validate required fields (`description`, `amount`, `category`, `date`, etc.) and return `400` with a clear message before calling into a service — services assume validated input.

## 4. Error Handling & Logging
* **No Bare Throws Reaching the Client:** Controller functions wrap service calls in `try/catch` and translate thrown errors into the standard JSON envelope with an appropriate status code (`400` validation, `404` not found, `401` auth, `500` unexpected). A caught error must never leave the promised database write silently unconfirmed to the frontend — if the write already succeeded before the failure point, that ordering itself is a bug to fix, not just a symptom to catch more gracefully.
* **Server Logs:** `console.error` is fine in this project's current dev-oriented logging (see `middleware/auth.js`, controllers) — always log the actual `error` object, not just a generic string, so failures like `TypeError: X is not a function` are visible immediately instead of being masked by a generic "Server Error" message.

## 5. Authentication (Clerk Exclusive)
* **Single Source of Truth:** Clerk is the only auth provider. No Passport.js, Firebase Auth, custom bcrypt/JWT session issuance, or any other auth library — `bcryptjs` and `jsonwebtoken` remain in `backend/package.json` only as leftover/legacy dependencies and should not be reintroduced into new auth code.
* **Frontend:** Import `ClerkProvider`, `useAuth`, `useUser`, `useClerk` from `@clerk/clerk-react`. Wrap the whole app in `ClerkProvider` (`main.jsx`); gate authenticated routes with the app's own `ProtectedRoute` wrapper (`App.jsx`), which reads `isSignedIn`/`loading` from the app's `AuthContext` (itself backed by Clerk's hooks — see rule above on `getToken()`).
* **Backend:** Protect Express routes with `middleware/auth.js`, which verifies the Clerk session token via `@clerk/clerk-sdk-node`'s `createClerkClient(...).verifyToken()` and just-in-time provisions a matching `User` document. Never fall back to manual JWT secret verification for new routes.
* **OAuth Configuration:** Social login providers are configured exclusively through the Clerk Dashboard (https://dashboard.clerk.com). No OAuth client IDs or secrets should appear in this codebase or its `.env` files.
